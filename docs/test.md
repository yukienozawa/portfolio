## 1. テスト戦略
本プロジェクトは**「テスト込み実装」**を大前提とします。コードを作成する際、それに対応するテストコードが同一PR（プルリクエスト）内に存在しない場合は、成果物として認められません。

---

## 2. テストの役割分担と使用ツール

| テスト種別 | 対象・役割 | 使用ツール |
| :--- | :--- | :--- |
| **Unit Test** | 共通ロジック、バリデーション、MDN準拠の命名が機能しているかの検証 | **Vitest** |
| **API Test** | Expressコントローラー、認可Middleware（404応答）の振る舞い検証 | **Supertest + Vitest** |
| **E2E Test** | フロントエンド（`front`）からバックエンド（`api`）を通じた全体の疎通検証 | **Cypress** |

---

## 3. カバレッジ方針
- MVPフェーズにおいては、網羅率（%）の数字を追求することよりも、**「主要な分岐（特に入力バリデーションと、認可Middlewareの404存在隠蔽応答）」**のテストケースを確実に網羅することを最優先とします。

---

## 4. テスト命名規則
テストケース名は、「何をインプットした時に、どうなるべきか」が人間およびAIに明確に伝わる記述的な英語または日本語で記載します。

* **構文**: `describe('対象機能/関数名', () => { it('条件の記述', () => { ... }) })`
* **具体例**:
    ```typescript
    describe('Authorization Middleware', () => {
      it('未認証のユーザーが/admin配下のAPIにアクセスした場合、HTTP 404を返すこと', async () => {
        // テスト実装（存在隠蔽の検証）
      });
    });
    ```
