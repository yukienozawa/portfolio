## 1. テスト戦略
本プロジェクトは**「テスト込み実装」**を大前提とします。コードを作成する際、それに対応するテストコードが同一PR内に存在しない場合は、成果物として認められません。

---

## 2. テストの役割分担と使用ツール

| テスト種別 | 対象・役割 | 使用ツール (推奨案) |
| :--- | :--- | :--- |
| **Unit Test** | 共通ロジック、バリデーション、MDN準拠の命名が機能しているかの検証 | Vitest (または Jest) |
| **API Test** | Expressコントローラー、認可Middleware（404応答）の振る舞い検証 | Supertest + Vitest |
| **E2E Test** | フロントエンドからバックエンドを通じた疎通、Firebase認証エミュレート | Cypress (または Playwright) |

---

## 3. カバレッジ方針
- MVPフェーズにおいては、網羅率（%）の追求よりも**「主要な分岐（特に入力バリデーションと認可Middlewareの404応答）」**のテストケース網羅を最優先とします。

---

## 4. テスト命名規則
テストケース名は、「何をインプットした時に、どうなるべきか」が人間およびAIに明確に伝わる記述的な英語または日本語で記載します。

* **構文**: `describe('対象機能/関数名', () => { it('条件の記述', () => { ... }) })`
* **具体例**:
    ```typescript
    describe('Authorization Middleware', () => {
      it('未認証のユーザーが/adminにアクセスした場合、HTTP 404を返すこと', async () => {
        // テスト実装
      });
    });
    ```
