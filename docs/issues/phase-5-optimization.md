## 🗄️ タスク1：実績画像データの保存先を AWS S3 へ移行 (Issue #13)

### 1. 目的
MySQLデータベース内に直接Base64/バイナリ（LongText/Blob）で画像を保存する暫定運用を廃止し、将来的なDB容量の肥大化とパフォーマンス低下を根本的に防ぐため。

### 2. 対象領域
- `api` (Express / Prisma)
- `front` (Next.js)
- AWSインフラ（S3バケット）

### 3. 実装内容
- **バックエンド**: `aws-sdk`（または `@aws-sdk/client-s3`）を導入。実績登録API（`POST /api/admin/achievements`）の画像受信時、データをAWS S3へアップロードし、DBにはその「公開URLの文字列」のみを保存するよう仕様を変更する。
- **データベース**: `api/prisma/schema.prisma` の `Achievement` モデルの `imageData` を、URLを保持する型（文字列）へリファクタリングする。
- **フロントエンド**: 画像のBase64変換処理を廃止、またはS3の公開URLから直接 `next/image` で描画する形へ修正する。

### 4. 完了条件
- [ ] 管理画面からアップロードした画像が、AWS S3バケット内に安全に保存されること。
- [ ] `GET /api/achievements` で取得したS3のURLをもとに、フロント側で画像が高速に表示されること。

## ⚡ タスク2：高頻度アクセスAPIへの Redis キャッシュ層の導入 (Issue #14)

### 1. 目的
ポートフォリオのトップや実績一覧など、不特定多数から高頻度でアクセスされる公開APIが、都度MySQLにクエリを投げるのを防ぎ、レスポンス速度の爆速化とDB負荷の軽減を両立するため。

### 2. 対象領域
- `api` (Express)
- Docker環境（`compose.yaml` へ Redis コンテナの追加）

### 3. 実装内容
- `compose.yaml` に公式の `redis:7` などのイメージを追記し、Dockerでキャッシュサーバーを起動する。
- `GET /api/achievements` のコントローラー直前でRedisキャッシュをチェックする。
  * **キャッシュが存在する場合（Hit）**: DBにアクセスせず、Redisからデータを即座に返却する。
  * **キャッシュが無い場合（Miss）**: 通常通りMySQLからデータを引き、それをRedisに一定時間（TTL設定）保存してから返却する。
- **データ一貫性**: 管理者が実績を新規登録（`POST`）した瞬間に、古いRedisキャッシュを自動で削除（パージ）するロジックを仕込む。

### 4. 完了条件
- [ ] 2回目以降の `GET /api/achievements` のレスポンスタイムが劇的に高速化（ミリ秒単位）すること。
- [ ] 実績を追加した際、古いキャッシュが破棄され、新しい実績が即座に画面に反映されること。

## 🧪 タスク3：Firebase Emulator Suite の導入による完全ローカル自動テスト化 (Issue #15)

### 1. 目的
CI/CD（GitHub Actions等）やローカルの自動テストにおいて、本物のFirebaseサービスに通信することなく、認証・認可の結合テストを100%スタンドアロンかつ高速に完結させるため。

### 2. 対象領域
- `api`（テスト環境）
- `front`（テスト環境）
- 開発インフラ環境（Firebaseの設定）

### 3. 実装内容
- プロジェクト内に `firebase.json` を配置し、`Firebase Emulator Suite`（Authenticationエミュレータ）を起動できるようにする。
- テスト実行スクリプト（`npm run test` 等）の起動時、環境変数をエミュレータのローカルポート（例: `localhost:9099`）に向き先を切り替える設定を行う。
- これにより、モック（Mock）ではない、本物の挙動に近い認証トークンの検証テストをローカルだけで完結させる。

### 4. 完了条件
- [ ] 外部のインターネット環境を遮断した状態でも、認証が絡むAPIテストやCypress E2Eテストがすべて正常に走り、合格すること。

## 📣 タスク4：問い合わせ通知の非同期 Queue 化と Slack Block Kit 装飾 (Issue #16)

### 1. 目的
一般ユーザーが問い合わせを送信した際、Slack等への外部通知処理（ネットワーク通信）が万が一遅延・障害を起こしても、ユーザーへの画面レスポンス（200 OK）を一切待たせず瞬時に返す（レジリエンス・体験向上）ため。

### 2. 対象領域
- `api` (Express)
- メッセージキュー基盤（BullMQ ＋ Redis等、またはメモリキュー）

### 3. 実装内容
- `POST /api/contact` を受け取った際、コントローラー内で直接Slackを呼び出すのを廃止する。
- データをDBに保存したら、即座に「通知タスク」としてバックグラウンドのジョブキュー（Queue）に放り込み、ユーザーには即座に「送信完了」を応答する。
- 裏側で待機している別プロセス（Worker）がキューからジョブを安全に拾い上げ、Slackの `Block Kit` を用いたリッチで美しいレイアウト（お名前、メール、本文が見やすく装飾されたデザイン）で通知を送信する。

### 4. 完了条件
- [ ] 問い合わせボタンを押した瞬間の画面のフリーズがゼロになり、一瞬で完了画面に切り替わること。
- [ ] Slack側に、Block Kitで綺麗に装飾された問い合わせ内容が時差なく通知されること。
