## 概要
開発標準に基づき、プロジェクト全体（front/api）の「静的解析（ESLint）」「コード成形（Prettier）」「単体テスト（Vitest）」の環境を構築します。

品質保証講義内容（単体テストの意義、仕様から考えるアプローチ、TDDの利点、カバレッジ、CIによる自動化）をすべてタスクに分解し、チーム開発で通用する高品質なプロダクト管理を実践します。

## 🛠️ 開発環境の構築タスク

### 🟩 1. フロントエンド側（front フォルダ）の環境構築
- [ ] **【テスト本体の導入】** ターミナルで `front` の部屋に移動し、テストツールの本体（`vitest`）をインストールする
- [ ] **【整形ツールの導入】** フロントのコードの見た目を整えるツール（`prettier`）をインストールする
- [ ] **【コード規約の定義】** `.prettierrc` ファイルを作成・保存し、インデント（スペース2）、セミコロン（あり）、シングルクォートの共通ルールを定義する
- [ ] **【ツールの競合回避】** Next.js標準の `ESLint` が Prettier の見た目ルールと衝突してケンカしないよう、仲直りさせる設定（`eslint-config-prettier`）を導入・連携させる
- [ ] **【起動コマンドの設定】** `package.json` の `scripts` に、ボタン一発でテストが起動するコマンド（`"test": "vitest"`）を1行追加する

### 🟦 2. バックエンド側（api フォルダ）の環境構築
- [ ] **【整形ツールの導入】** 一度外に出て `api` の部屋へ大移動し、コードの見た目を整えるツール（`prettier`）をインストールする
- [ ] **【コード規約の同期】** フロントと同じ見た目のルールになるよう、`api` フォルダの直下にも `.prettierrc` ファイルを作成・保存する
- [ ] **【テスト本体の導入】** バックエンド用のテストツールの本体（`vitest`）をインストールする
- [ ] **【起動コマンドの設定】** `package.json` の `scripts` に、同じくテストを起動するためのコマンド（`"test": "vitest"`）を追加する

---

## 🟪 3. 品質管理（QA）の視点を活かした「テスト」の実装

- [ ] **【仕様から考える】** 関数・APIの「～べきである」という仕様から、OKパターン（正常系）の検証項目を洗い出す
- [ ] **【仕様から考える】** エラーや不正データに対するNGパターン（異常系）の検証項目を洗い出す
- [ ] **【TDDの意識】** コード修正前に「インプットとアウトプット」を明確にし、テストが通るように既存プログラムを型安全にリファクタリングする
- [ ] **【テストしやすさの追求】** 「一つのファイルに一つの機能」を意識し、可読性と保守性の高いコードに整える
- [ ] **【カバレッジ管理】** Vitestを利用して、テストプロセスがどれだけのコードを網羅しているか指標を意識して実行する

#### 🔄 （発展）品質管理（QA）の3階層に沿った段階的な検証
- [ ] 🧪 **（単体テスト）最小単位で確認する**
      目的：最小単位のコードが、設計通りに正しく動くことを孤立した状態で保証すること
  - フロント（Vitest）とバック（Vitest）それぞれで、関数やロジック単体が正しく動くか検証する（★本タスクではこの「箱づくり」までを担保）
- [ ] 🤝 **（結合テスト）組み合わせて確認する**
      目的：「書いたコードが、本当にデータベースと正しく連携できているか？」を検証すること
      環境：Docker (MySQLコンテナ) の立ち上げが必須
  - フロントとバックエンドを連携させ、APIから取得したデータが画面に正しく反映されるか検証する（正常系・異常系）
- [ ] 🌐 **（システムテスト / E2Eテスト）全体を通して確認する**
      目的：フロントエンドの画面からAPI、データベース、場合によっては外部サービスまで、システム全体が「ユーザーの期待通りに動くか」を検証すること
      環境：Docker (MySQLコンテナ) の立ち上げが必須
  - ユーザーが実際にブラウザを操作する一連の流れ（データの入力〜登録〜表示）が、システム全体で破綻なく動くか最終確認する

## 🧪 動作確認・検証コマンド（QA）
すべてのインストールと設定ファイルの準備が終わったら、以下のコマンドが両方の部屋でエラーなく起動することを確認します。

```bash
# フロントエンド側の動作確認
cd front
npm run test  （または npx vitest）

# バックエンド側の動作確認
cd ../api
npm run test  （または npx vitest）


### 🚀 4. 将来的な発展を見据えた設計意識（Git & CI）
- [ ] **【Git branchの在り方】** 現在の `feature`（作業場所）から `develop`（開発場所）へマージする流れを意識してコミットを積む
- [ ] **【CI（継続的インテグレーション）】** 将来的にGitHub Actions等で「マージ前にESLint/Prettier/テストを自動で動かして命令を出す」ことを想定し、ローカル環境で全てのチェックを「Green（合格）」のステータスにする

---
## 🔍 最終的な検証コマンド
各フォルダ内で以下の2つのコマンドを実行し、どちらの部屋でもエラーなしで合格すれば「課題クリア（マージ可能状態）」となります。

1. `npx eslint src` （静的解析エラーがゼロであること）
2. `npm run test` （すべての単体テストが合格すること）
